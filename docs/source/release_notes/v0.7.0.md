# GRIDR v0.7.0 — Release Notes

**Release date:** 2026-09-30  
**Type:** FFT Filtering API and Feature Release

This release rewrites the FFT filtering layer. The options become plain strings instead of enumerations, the geometry of a call is computed up front and exposed as an immutable plan, and three features that were previously guarded or missing are implemented: rational decimation, the production window in the raster chain, and the `"valid"` output mode.

Every breaking change is concentrated in `core.convolution.fft_filtering` and `chain.fft_filtering_chain`. Most of them are renames and a switch from enumeration members to strings, so migrating is largely a search and replace; see the migration section at the end.

Two user's guides ship with this release, *FFT Filtering Core* and *FFT Filtering Chain*, as series of executable notebooks. They cover the features below in detail.

The rest of the release is invisible from Python:
  - the Rust code is split into a two-member Cargo workspace, so the core engine can be consumed as a standalone Cargo dependency, with the public Python API unchanged.
  - the Rust code is now compatible with the 2024 edition, which also bumps the minimum required Rust version to 1.85."

---

## FFT Filtering

### Rational decimation

`zoom` accepts a rational factor `P / Q`, previously guarded by `assert zoom == 1`. Only pure decimation is implemented, so the factor must reduce to `1 / Q`.

`decimation` selects which sample of each block of `Q` is kept, `"leading"` or `"centered"`.

```python
out, window = fft_array_filter(
    image, kernel, boundary="reflect", out_mode="same",
    zoom=(1, 4), decimation="centered",
)
```

The kernel remains the only anti-aliasing filter in the chain, and choosing a cutoff matched to the factor is up to the caller. The *Zooming out and aliasing* tutorial shows how to check one against the other.

### Production window in the chain

`fft_filtering_oa_strip_chain` accepts `win`. Strips are cut over the window and not over the raster height, and each read is restricted to the window extended by the kernel margins, so a small window on a large raster costs a small read.

Sizing and georeferencing the output dataset is the caller's job, and the *Production window and decimation* tutorial of the chain guide gives the recipe.

### Filter plan

`build_plan` derives the whole geometry of a call from the input shape alone, without allocating data, and returns an immutable `FilterPlan` that `fft_array_filter` accepts through `plan=`.

```python
plan = build_plan(tile_shape, kernel, boundary="symmetric", out_mode="same")

for tile in tiles:
    out, _ = fft_array_filter(tile, kernel, plan=plan)
```

Tiled schedulers gain twice: the geometry is computed once for many tiles, and the output can be sized before a single pixel is read, `fft_array_filter_output_shape` consuming the same plan as the execution path.

### More options

`"symmetric"`, `"edge"`, `"wrap"` and `"constant"` join `"reflect"` as boundary policies. The `"valid"` output mode is implemented in the core layer, where it previously raised `NotImplementedError`; the overlap-add chain still refuses it.

`dtype` pins the working dtype, so a `float32` raster convolved with a `float64` kernel no longer silently doubles its memory footprint. `method` picks the backend convolution method.

Both guides state the restrictions that come with these options, in particular those attached to `"wrap"`.

## 🛡️ Stability fixes

- **Crash on `win=None` with an `axes` subset.** Non-target axes were filled with `(None, None)`, producing an object-dtype window that failed later with a `TypeError`.
- **Cross-enumeration equality.** `BoundaryPad.REFLECT == ConvolutionOutputMode.FULL` evaluated to `True`, both being `IntEnum` members of value 2. The enumerations are gone, which removes the class of bug rather than the instance.
- **Strip shorter than the kernel.** `check_oa_strip_size` did not force the monolithic path, leaving the overlap-add buffer under-sized.

## 📚 Breaking changes

All of them are in the FFT filtering modules.

### Options are plain strings, not enumerations

`BoundaryPad` and `ConvolutionOutputMode` are removed. Boundary policies are the `numpy.pad` mode strings, the ones `array_grid_resampling` already takes, and output modes those of `scipy.signal.convolve`. `None` is accepted for no boundary synthesis, and zero padding is spelled `"constant"`, as in NumPy, not `ZERO`.

```python
# Before
fft_array_filter(arr, fil, boundary=BoundaryPad.REFLECT,
                 out_mode=ConvolutionOutputMode.SAME)

# After
fft_array_filter(arr, kernel, boundary="reflect", out_mode="same")
```

### `fil` renamed `kernel`

In the core functions and in the chain functions alike. Every option beyond `arr`, `kernel` and `win` is keyword-only.

```python
# Before
fft_array_filter(arr, fil, win, boundary, out_mode)
fft_filtering_oa_strip_chain(ds_in, ds_out, band, fil, boundary, out_mode)

# After
fft_array_filter(arr, kernel, win, boundary=..., out_mode=...)
fft_filtering_oa_strip_chain(ds_in, ds_out, band, kernel, boundary, out_mode)
```

### Other signature changes

- At most one non-`"none"` boundary policy per call. Sides declare whether they are padded, not how, and mixing two now raises `ValueError` instead of depending on set iteration order.
- `fft_array_filter_output_shape` returns a `tuple[int, ...]` instead of an `np.ndarray`.
- `axes` is normalized as a set and returned sorted, consistent with `scipy.signal.oaconvolve`. Repeated axes are rejected.
- `win` no longer accepts per-axis `None` bounds.
- `check_oa_strip_size` takes the number of produced rows, `nrow`, instead of the input array.

### Renames and removals

- `fft_odd_filter` → `pad_kernel_to_odd`
- `get_filter_margin` → `kernel_margin`
- `fft_array_filter_check_data` and `pad_array` are superseded by `build_plan`

## 🦀 Rust workspace split

The single Rust crate is split into a two-member Cargo workspace:

| Crate | Contents | Depends on PyO3 |
|-------|----------|-----------------|
| `rust/gridr` | Pure-Rust core engine | no |
| `rust/gridr-py` | PyO3 bindings, `cdylib` only | yes |

The core engine can now be consumed as a standalone external Cargo dependency, without pulling `pyo3` or `numpy` into a Rust-only project. The public Python API and its runtime behaviour are preserved exactly.

The Rust code is also upgraded to edition 2024, which requires Rust 1.85.1 or later to build from source.

## 🔧 Migration

1. Replace the enumeration members by their string equivalents. `BoundaryPad.REFLECT` becomes `"reflect"`, `ConvolutionOutputMode.SAME` becomes `"same"`, and `BoundaryPad.ZERO` becomes `"constant"`.

2. Rename `fil` to `kernel` at every call site, core and chain, and pass the remaining options by keyword.

3. Check the calls that mixed two boundary policies. They now raise instead of silently picking one.

4. *(If you consume the predicted shape)* `fft_array_filter_output_shape` returns a tuple. Code doing arithmetic on the returned array needs `np.asarray` around it.

5. *(If you call `check_oa_strip_size` directly)* Pass the number of produced rows instead of the input array.

6. *(Optional)* If you filter many tiles with the same geometry, build the plan once and pass it through `plan=`.

## Internals

None of this changes the Python API:

- The core module is reorganised into helpers, plan construction and execution. Validation happens once, in `build_plan`, instead of being spread across several helpers.
- Boundary padding delegates to `array_pad.pad_inplace`, so the convolution input is allocated once whatever the number of padded sides.
- One vocabulary for boundary handling across GridR: the strings accepted here are those `array_grid_resampling` already takes.
- The test suites were refactored, and created for the chain module.
- Rust doctests were ignored and are now fixed.

## 📦 Installation

```bash
pip install --upgrade gridr
```

Wheels are now built by a GitHub Actions workflow for manylinux_2_28 x86_64, macOS on Intel and Apple Silicon (ARM64), and Windows x86_64. A single `cp310-abi3` wheel per platform and architecture covers Python 3.10 to 3.14 and is published on PyPI.

AVX2 and FMA flags are applied on every x86_64 target and their presence is verified in the compiled binary. Requirements:

- Python ≥ 3.10
- x86_64 with AVX2 and FMA, or a build from source on other platforms
- Rust ≥ 1.85.1 to build from source, edition 2024
